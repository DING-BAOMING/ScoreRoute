## 故障排查

### 503错误 (Upstream Timeout)
- **表现**: 请求返回503，latency_ms为300000+
- **原因**: 上游API超时，本系统设置300秒超时
- **排查方法**: 
  1. 检查日志中的error字段
  2. 直接使用curl测试上游API
  3. 确认API Key是否有效
- **解决方案**: 禁用或修复问题渠道

### 示例: 测试NVIDIA API
```bash
curl -X POST "https://integrate.api.nvidia.com/v1/chat/completions" \
  -H "Authorization: Bearer <API_KEY>" \
  -d '{"model":"z-ai/glm5","messages":[{"role":"user","content":"Hi"}],"max_tokens":5}'
```

## 模型评分机制

### 评分算法
| 指标 | 权重 | 说明 |
|------|------|------|
| 成功率 | 32% | 成功请求占总请求的比例 |
| 延迟分数 | 24% | 基于平均延迟计算，延迟越低分数越高 (阈值30秒) |
| 稳定性 | 24% | 基于样本量，样本越多越可靠 (<5样本0.5分, 5-10样本0.5-0.8, 10-30样本0.8-1.0, 30+样本1.0) |
| 用户评分 | 20% | 用户对模型的1-100评分，标准化到0-1 |

### 评分公式
```
Score = 成功率 × 0.32 + (1 - 平均延迟/30000) × 0.24 + 稳定性分数 × 0.24 + 用户评分/100 × 0.20
```

### 显示说明
- 显示格式: `渠道/格式/类型/模型名称` (如: `MiniMax/openai/chat/MiniMax-M2.5`)
- 显示所有启用的模型（包括调用次数为0的新模型）
- 按评分降序排列
- 实时从日志数据计算
- 用户评分会同步到同一模型的不同渠道（如 minimaxai/minimax-m2.5 和 MiniMax-M2.5 共享评分）

## 轮询机制说明

### 轮询策略
- **轮询方式**: 渠道优先 + 模型次之 (Channel-First, Model-Second)
- **轮询顺序**: 先按渠道的调用次数(call_count)升序选择渠道，再在选中渠道内按模型的调用次数(call_count)升序选择模型
- **排序规则**: 
  - 渠道: `ORDER BY c.call_count ASC, c.id ASC`
  - 模型: `ORDER BY m.call_count ASC, m.id ASC`
- **计数更新**: 每次请求会同时递增渠道和模型的 call_count

### 请求模型名称说明
| 模型名称 | 行为 |
|---------|------|
| 具体模型名 | 使用指定模型 |
| `auto` / `Auto` | 按Token的format+type轮询同类型所有模型 |
| `AUTO` / `POLL_ALL` | 轮询所有模型（不限format+type） |
| `__POLL_ALL__` (Token配置) | 轮询所有模型（不限format+type） |
| `__AUTO__` (Token配置) | 按Token的format+type轮询同类型所有模型 |

### Token模型名称配置说明
| Token model_name | 行为 |
|-----------------|------|
| 留空 | 按Token的format+type轮询同类型所有模型 |
| `__POLL_ALL__` | 轮询所有模型（不限format+type） |
| `__AUTO__` | 按Token的format+type轮询同类型所有模型（与留空效果相同） |
| 具体模型名 | 固定使用该模型 |

### 示例
假设有2个渠道，每个渠道2个模型：
- JDBook: glm5, minimax-m2.5
- xuetao: glm5, minimax-m2.5

轮询顺序（渠道优先，模型次之）:
1. JDBook/glm5 (JDBook调用1次，JDBook内glm5调用1次)
2. xuetao/glm5 (xuetao调用1次，xuetao内glm5调用1次)
3. JDBook/minimax-m2.5 (JDBook调用2次，JDBook内minimax调用1次)
4. xuetao/minimax-m2.5 (xuetao调用2次，xuetao内minimax调用1次)
5. JDBook/glm5 (JDBook调用3次，JDBook内glm5调用2次)
6. xuetao/glm5 (xuetao调用3次，xuetao内glm5调用2次)
... 以此类推

## 2024-04-11 代码修复

### 本次修复的问题

#### 1. Nil Pointer Dereference (严重)
**文件**: `internal/service/dispatcher.go`
**问题**: 当用户请求一个不存在的模型名称时，`GetByName()` 返回 `nil, nil`，后续访问 `modelItem.ChannelID` 会导致 panic。
**修复**: 在 `Dispatch()` 和 `DispatchStream()` 函数的 `GetByName` 调用后，添加 `nil` 检查并返回错误。

```go
} else if modelName != "" {
    modelItem, err = d.modelService.GetByName(modelName)
    if err != nil {
        return nil, 0, fmt.Errorf("failed to get model: %w", err)
    }
    if modelItem == nil {
        return nil, 0, fmt.Errorf("model not found: %s", modelName)
    }
}
```

#### 2. 渠道凭证测试错误检测 (中等)
**文件**: `internal/service/channel.go`
**问题**: `TestCredentials` 只检查 `status >= 500` 作为错误，遗漏了 `401 Unauthorized` 和 `403 Forbidden`。
**修复**: 改为检查所有 `status >= 400` 作为错误。

```go
if resp.StatusCode >= 400 {
    return false, fmt.Errorf("request failed with status: %d", resp.StatusCode)
}
```

#### 3. Token Used 解析失败日志 (低)
**文件**: `internal/service/dispatcher.go`
**问题**: 当 `json.Unmarshal` 解析响应体失败时，错误被静默忽略，导致 `token_used` 始终为 0。
**修复**: 添加错误日志记录，帮助诊断 NVIDIA API 响应格式问题。

```go
if err := json.Unmarshal(body, &relayResp); err != nil {

    }
    log.Printf("failed to unmarshal response for token usage: err=%v, body=%s, model=%s", err, string(body[:bodyLen]), modelItem.Name)

    tokenUsed = relayResp.Usage.TotalTokens
}
```

## 流式请求 Token 追踪解决方案

### 问题背景
NVIDIA NIM API 在流式响应中不返回 `usage` 信息，所有 SSE chunk 的 `usage` 都为 `null`。这导致流式请求的 `token_used` 始终为 0。

### 行业成熟方案

| 方案 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **Tiktoken 本地计数** | 使用 `tiktoken-go` 库对响应文本进行分词计数 | 准确、不依赖上游API、支持多种模型 | 需要导入新库 |
| **Shadow Request** | 同时发送一个非流式请求用于获取token数 | 准确、兼容性好 | 增加API调用成本(50%) |
| **响应长度估算** | 根据响应文本长度估算token数 | 简单、无需额外API调用 | 不准确(约70%准确度) |
| **Async轮询(NVIDIA)** | 使用request_id轮询获取完整结果 | 准确 | NVIDIA特定方案 |

### 参考项目
- **One API**: 使用 `TIKTOKEN_CACHE_DIR` 环境变量配置本地token计数
- **OpenAI Cookbook**: 推荐使用 `tiktoken` 进行本地token计数

### 推荐实施方案
**方案**: Tiktoken 本地计数 + 流式响应后处理

**实现步骤**:
1. 引入 `tiktoken-go` 库 (https://github.com/pkoukk/tiktoken-go)
2. 在流式响应结束后，对响应内容进行分词计数
3. 将计数结果记录到日志

**优点**:
- 不依赖上游API返回usage
- 适用于所有支持Tiktoken编码的模型
- 成本为零（无需额外API调用）

**注意事项**:
- Tiktoken 编码与实际模型的编码可能略有差异
- 需要为不同模型选择正确的编码 (cl100k_base, o200k_base等)

## 2026-04-12 额外评分系统（惩罚/奖励机制）

### 功能概述

额外评分系统用于实现模型轮转调用，通过惩罚被调用过的模型和奖励未被调用的模型来动态调整模型评分。

### 惩罚机制

**原理**: 当任意模型被调用时，ALL模型都会被扣除一定分数（实现轮转调用）。

**配置参数**:
- `punishment_rounds`: 惩罚持续轮数（默认5轮）
- `punishment_score`: 每次调用的惩罚分数（默认5分）

**衰减规则**:
- 每当有新的API请求时，ALL现有惩罚记录的分数都会减少1分
- 惩罚分数 = 原始惩罚分数 - (当前全局请求轮次 - 惩罚创建时的请求轮次) × 每次衰减分

**关键点**:
- 每次请求会给所有模型添加惩罚，而非仅给被调用的模型
- 这样可以有效实现模型轮转，防止总是调用同一模型

**示例**:
假设有2个模型，惩罚分数=5，惩罚轮数=5

| 请求 | 调用的模型 | 所有模型惩罚记录 | 模型A评分变化 | 模型B评分变化 |
|------|-----------|-----------------|-------------|-------------|
| 1 | 模型A | 所有模型-5分 | 99 - 5 = 94 | 89 - 5 = 84 |
| 2 | 模型A | 所有模型现有-4分, 再-5分 | 99 - 4 - 5 = 90 | 89 - 4 - 5 = 80 |
| 3 | 模型B | 所有模型现有-3分, 再-5分 | 99 - 3 - 5 = 91 | 89 - 3 - 5 = 81 |
| 4 | 模型B | 所有模型现有-2分, 再-5分 | 99 - 2 - 5 = 92 | 89 - 2 - 5 = 82 |

### 奖励机制

**原理**: 当新模型被添加到系统时，该模型会获得奖励分数（用于吸引注意新加入的模型）。

**配置参数**:
- `reward_hours`: 奖励持续时间（默认24小时）
- `reward_score`: 新模型获得的奖励分数（默认5分）

**触发条件**:
- 仅当新模型被创建时触发
- 已存在的模型不会被奖励

**衰减规则**:
- 奖励是基于时间的线性衰减
- 奖励分数 = 原始奖励分数 × (1 - 已过分钟数 / 总分钟数)
- 例如：5分奖励持续24小时，每分钟衰减约0.0035分

**示例**:
新模型创建后，奖励分数随时间衰减：

| 时间 | 奖励分数 |
|------|---------|
| 0分钟 | 5.00分 |
| 1小时 | 4.79分 |
| 12小时 | 2.50分 |
| 24小时 | 0分 |

## 2026-04-12 Bug修复：expires_at扫描错误

### 问题描述

设置渠道的rate limits（频率限制）后，该渠道在API调用中无法被读取，导致：
- 渠道列表中看不到该渠道
- 模型评分页面无法获取该渠道下模型的统计信息
- 设置expires_at后scan失败

### 错误信息

```
sql: Scan error on column index 9, name "expires_at": unsupported Scan, storing driver.Value type string into type *time.Time
```

### 根因分析

1. **数据不一致**: channels表的expires_at列被ALTER TABLE添加后，某些行的expires_at值被存储为字符串格式（如"2026-05-05"）而非正确的DATETIME格式
2. **Go扫描失败**: 当SELECT查询返回字符串格式的expires_at时，SQLite驱动无法将字符串扫描到`*time.Time`类型
3. **影响范围**: 任何在expires_at列中存储了无效格式字符串的渠道都会出现此问题

### 修复方案

在repository层的所有查询函数中，将`expires_at`字段先扫描到`sql.NullString`，然后使用`time.Parse`解析多种可能的日期格式：

```go
func parseExpiresAt(expiresAtStr sql.NullString) *time.Time {
    if expiresAtStr.Valid && expiresAtStr.String != "" {
        formats := []string{
            "2006-01-02 15:04:05",
            "2006-01-02T15:04:05Z07:00",
            "2006-01-02",
        }
        for _, format := range formats {
            t, err := time.Parse(format, expiresAtStr.String)
            if err == nil {
                return &t
            }
        }
    }
    return nil
}
```
